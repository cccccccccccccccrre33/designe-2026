# Маршрутизация моделей и контроль расходов

Код: `src/llm/router.ts`, `src/budget/ledger.ts`. Конфигурация:
`studio/policies/models.json`, `studio/policies/budget.json`.

## Классы задач

Агент не выбирает модель. Каждый вызов объявляет **класс задачи** и требования:

| Класс | Уровень по умолчанию | Нужны изображения | Пример |
|---|---|---|---|
| `classify` | economy | нет | тип инициативы, срочность |
| `extract` | economy | нет | правки из сообщения владельца |
| `dedupe` | economy | нет | похожа ли находка на бэклог |
| `position` | main | нет | позиция специалиста |
| `brief` | main | нет | синтез брифа и направлений |
| `spec` | main | нет | Screen Spec, Motion Spec, Photo Brief |
| `critique` | vision | да | оценка рендеров по рубрике |
| `science` | main | нет | Technical Note советника |
| `arbiter` | premium | да | спор между лидерами |

Отправка Telegram, статусы, подсчёт стоимости, коммиты — **не** классы задач.
Это код без LLM.

## Алгоритм выбора

1. Кандидаты класса берутся из `assignments[class]` в порядке «дешевле → дороже».
2. Отбрасываются модели: неактивные, без нужной модальности, с контекстом меньше
   оценки входа, без проверенной цены, с открытым circuit breaker, недоступные
   в регионе, из того же семейства, что автор (для критики — если есть
   альтернатива).
3. Если в `studio/evals/results.json` есть оценка модели для класса — берётся
   первая модель, чья оценка ≥ порога класса. Без оценок — первая по порядку.
4. Резерв бюджета на оценку стоимости; отказ → `BudgetExceeded`.
5. Вызов. Ошибка сети/квоты → 1 ретрай с паузой, затем следующий кандидат.
   Невалидный JSON → 1 попытка ремонта той же моделью, затем следующий кандидат.
6. Максимум попыток на вызов — 3. После — `ModelChainExhausted` и пауза
   инициативы с понятной причиной.
7. Фактические токены из `usage` закрывают резерв; разница возвращается.

Circuit breaker: 3 ошибки подряд у модели → модель исключается на 10 минут.

## Почему не встроенный Intelligent Prompt Routing

Он выбирает только внутри одного семейства и по неизвестному нам критерию. Нам
нужно межпровайдерное переключение, правило независимости критика и учёт денег
по каждой роли.

## Бюджет

Лимиты (значения по умолчанию, меняются в `budget.json`):

| Область | По умолчанию |
|---|---|
| Инициатива | $5 |
| День | $10 |
| Месяц | $100 |
| Генерация изображений на инициативу | $2 |
| Premium-арбитраж в месяц | $10 |
| Автономные инициативы в месяц | 20% месячного |
| Вызовов LLM на инициативу | 60 |

Резерв проверяет **все** области сразу: инициатива, день, месяц, категория.
Параллельные вызовы не могут превысить лимит, потому что резерв выдаётся
атомарно.

Пороги 50% / 80% / 95% (по дню и месяцу):

- **50%** — запись в журнал, строка в `/budget`.
- **80%** — одно уведомление; отключаются необязательные шаги (premium-арбитр,
  третий вариант); автономные инициативы не стартуют.
- **95%** — новые инициативы не стартуют; текущие завершают только обязательные
  шаги.
- **100%** — резерв не выдаётся; инициатива на паузе; владелец получает одно
  сообщение с причиной и кнопкой продолжить после изменения лимита.

Отключение необязательного шага всегда записывается в отчёт инициативы и
упоминается в карточке («проверка арбитром не проводилась: лимит бюджета»).
Тихой деградации нет.

## Ориентировочная стоимость одной инициативы «главный экран»

| Шаг | Вызовов | Модель (оценка) | ≈ USD |
|---|---|---|---|
| Триаж | 1 | economy | 0.001 |
| Позиции 5 ролей | 5 | main | 0.02 |
| Бриф | 1 | main | 0.01 |
| 3 варианта Screen Spec + фото-бриф | 6 | main | 0.06 |
| Фото: 6 поисковых + 1 финальное | 7 | Stable Image Core/Ultra | 0.35 |
| Критика 3 вариантов, 4 критика | 4 | vision | 0.10 |
| Арбитр (если нужен) | 0–1 | premium | 0–0.14 |
| Доработка ×2 + повторная критика | 6 | main + vision | 0.08 |
| Итого | ~30 | | **≈ 0.6–0.8** |

Реальные цифры появятся после первых живых запусков — `/budget` показывает
расход по моделям, ролям и инициативам.

## Сравнительное тестирование (этап 3)

`studio/evals/tasks.json` — 10 реальных задач DRIVE&KAVA из брифа (анализ
главной, переработка карточки, UX кастомайзера, сравнение композиций, критика
фотокарточки, художественное направление, анализ перехода, проверка гипотезы,
техническая спецификация, классификация замечаний). Каждая задача имеет
объективные проверки (схема, найденные заранее известные проблемы, соблюдение
ограничений) и рубрику для судьи. Запуск `npm run eval -- --class critique` (или `--models kimi-k2.5,nova-2-lite`)
прогоняет кандидатов и пишет `studio/evals/results.json`: качество, найденные
проблемы, стоимость, время. Назначения меняются в `models.json` по
результатам — роли при этом не меняются.
